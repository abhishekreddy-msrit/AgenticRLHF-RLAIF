## Current models

- **Target:** `HuggingFaceTB/SmolLM2-135M-Instruct` (Transformers CPU)
- **Judge:** Ollama `tinyllama` (weak structured JSON; frequent hybrid/heuristic merge)
- **Embeddings:** Ollama `nomic-embed-text` present but unused in V0.1
- **Also local:** `llama3.1:8b` (OOMs as judge under low free RAM)

## Hardware reality check

- User reports RTX 4060, but **this session**: `nvidia-smi` fails, `torch 2.15.0+cpu`, `cuda=False`
- RAM ~16.8 GB total, often **&lt;3 GB free** with apps open
- Disk free ~13 GB
- Ollama models on disk ~5.8 GB

Implication: do **not** assume CUDA training. Prefer Ollama for larger-model *inference*; keep HF SmolLM2 for *trainable* DPO path.

## Architectural weaknesses

1. Target quality too low for demos (135M often incoherent/unsafe).
2. Judge TinyLlama cannot reliably emit rubric JSON → hybrid/heuristic reliance.
3. TF-IDF retrieval is weak; not persistent semantic memory.
4. HF PEFT adapters **cannot** be loaded into Ollama GGUF models.
5. Simultaneous HF + Ollama loads fight for RAM; unload discipline is partial.
6. UI is technical Streamlit dashboard, not product-grade.
7. `find_latest_adapter` previously could pick `/ref` (fixed in V0.1 late).
8. No dual-backend target abstraction (Ollama vs Transformers).

## Compatibility decision for V0.2

- **Playground target (quality):** Ollama Qwen instruct (~1.5B–3B)
- **Training + optimized inference:** keep HF SmolLM2 + existing LoRA adapter
- **Judge:** stronger Ollama Qwen (prefer 3B; fall back to 1.5B / llama3.1 if needed)
- **Retrieval:** Chroma + `nomic-embed-text` (already installed), TF-IDF fallback

This preserves a real end-to-end preference-optimization demo without claiming Ollama runs the LoRA adapter.
